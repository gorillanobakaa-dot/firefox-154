## 2. THE BUG THAT WAS FIXED TODAY (WebCodecs TypeError)

### The discovery that reframes everything

**WhatsApp Web does not use WebRTC media sections at all.** It encodes/decodes
call video **in-page via the WebCodecs API** and ships frames over an
`m=application` **DataChannel**. Proven from a `chrome://webrtc-internals` dump of
a **working Chromium call**:

```
PC 9-6 / 9-8 / 9-10  (all three identical)
  rtcConfiguration : {"alwaysNegotiateDataChannels":false}   <- NO iceServers
  offer m-lines    : ['application']                          <- NO audio, NO video
  candidate types  : {'host': 1}
  ICE              : checking -> connected
```

Therefore there is **no SDP codec negotiation**. The build's H.264-only WebRTC
codec policy (`DefaultCodecPreferences.cpp`) is **never consulted for WhatsApp**.

### Root cause

`WebCodecsUtils.cpp:609 IsSupportedVideoCodec()` correctly returns H.264-only
under `media.gorilla.hardware_only_mode`. **But** the same check had been
duplicated into the **config-validation** functions:

- `dom/media/webcodecs/VideoDecoder.cpp` → `VideoDecoderTraits::Validate()`
- `dom/media/webcodecs/VideoEncoder.cpp` → `VideoEncoderTraits::Validate()`

A `Validate()` failure means *"config is MALFORMED"* and surfaces to JS as
**`TypeError("IsConfigSupported: config is invalid: Unsupported codec under
hardware-only mode")`**. Per spec (`#check-configuration-support`) a
valid-but-unsupported codec must **resolve `{supported:false}`**. WhatsApp's
feature test hit the throw and aborted call setup permanently.

`CanDecode()` (VideoDecoder.cpp:198) and `VideoEncoderTraits::IsSupported()`
(VideoEncoder.cpp:351) **already** consult `IsSupportedVideoCodec()`, so the
correct answer was always reachable — the `Validate()` copies were redundant AND
harmful.

### Fix applied (both files), 2026-08-11

Deleted the check from **both `Validate()` functions**. Nothing else.
`WebCodecsUtils.cpp` untouched — **enforcement unchanged and absolute**.
`#include "mozilla/StaticPrefs_media.h"` deliberately **retained** in both files:
removing an include from a unified-build bundle can break sibling TUs.

Marker: `// GORILLA OVERRIDE 2026-08-11:` in both files.

This restores Layer 1's own documented philosophy (`MEDIA_CODEC_LESSONS.md`):
`canPlayType()` returns `CANPLAY_NO` — a **clean** refusal — "so YouTube
negotiates H.264 MP4 without wasting RTP attempts". **A capability gate must
answer "no"; it must never throw.** The WebCodecs patch was added later, outside
the documented 6-layer gate, and broke that rule.

## 5. THE LIVE TASK — audio "waves" / pumping (DIAGNOSED, NOT FIXED)

**User's report:** sound "in waves coming and going like waves rolling up to the
shore". **The user explicitly does NOT want the loudness removed** — getting
decent volume is the entire point of that work. Goal: **keep the loudness, kill
the pumping.**

### Diagnosis: TWO 4:1 COMPRESSORS IN SERIES

The 2026-08-10 session shipped the same loudness fix **twice**:

1. **System level** — PipeWire **SC4** compressor sink (LADSPA `sc4m`, control
   order `0,3,150,-20,4,8,12`): threshold −20 dB, ratio 4:1, attack 3 ms, release
   150 ms, makeup +12 dB. Mic-verified **+10.5 dB RMS**. It is the **default
   sink** (`loudness_sink`). Armored `chattr +i`. Plus
   `loudness-volume-mirror.service` (0.75-power map), because a compressor
   upstream of the volume slider makes the slider feel dead.
2. **In-browser** — `dom/media/AudioStream.cpp` `AudioPsychoacousticEnhancer`
   **Stage 5b** envelope compressor with the **identical parameters**:
   `kCompThreshold 0.10 (-20 dBFS)`, `kCompSlope 0.75 (4:1)`,
   `kCompMakeup 4.0 (+12 dB)`, attack 3 ms / release 150 ms. Shipped in-source so
   *downloaders* get audible speakers.

**Both are live right now** — verified today:
```
systemctl --user is-active loudness-sink.service loudness-volume-mirror.service -> active active
pactl info | Default Sink: loudness_sink
AudioStream.cpp:922   mPsychoEnhancer->Process(buf, frames);   <- called in DataCallback
```

So the Firefox audio path is **source → browser Stage 5b (4:1) → system SC4 (4:1)
→ speakers**: effectively ~16:1 with ~+24 dB combined makeup and two 150 ms
release envelopes beating against each other. Music sits above −20 dBFS almost
continuously, so gain is perpetually clamping and releasing. **That is the
"waves".**

### The previous session PREDICTED this and never tested it

Brain atom `Loudness_compressor_shipped_in_source_and_published_2026_08_10_...`
says verbatim: *"If both feel over-dense together, **either alone suffices** —
browser stage limiter rarely engages post-compression."*

And its verification moved test streams **around** the system sink
(`pactl move-sink-input`), so each stage was measured **stage-by-stage but the
cascade was never auditioned end-to-end** on this machine. That gap is the bug.

### Fix options — ALL PRESERVE LOUDNESS (user requirement)

**(B) DO THIS FIRST — no-rebuild confirmation of the diagnosis.**
Temporarily bypass the system sink and listen to Firefox on Stage 5b alone:
```sh

pactl set-default-sink <hardware_sink>       # bypass loudness_sink; do NOT disable the service
# listen. If the waves vanish -> diagnosis confirmed.
pactl set-default-sink loudness_sink         # restore
```
Fully reversible, touches nothing permanent. During the test the loudness comes
from Stage 5b alone, so non-Firefox apps will be quieter — expected and temporary.

**(A) RECOMMENDED FIX — pref-gate Stage 5b, keep the system sink.**
Add a pref (e.g. `media.gorilla.psychoacoustic_enhancer.enabled`, **default true**
so downloaders keep the shipped loudness) and set it **false** in this machine's
`user.js` (`~/.mozilla/ff154-main/user.js`). Result: system SC4 keeps **every app**
loud (Telegram, system sounds, Firefox), only one compressor in the chain, pumping
gone, shipped build unchanged for everyone else.
Cost: a rebuild. **Note:** a `StaticPrefList.yaml` change may require a **full**
`./mach build`, not `build binaries` — classify per AGENTS.md before starting.

**(C) Retune instead of remove** — raise one stage's threshold or cut its makeup
so only one compressor does real work. Keeps both code paths, still cascades;
only if (A) is rejected.

**(D) NOT ACCEPTABLE** — disabling `loudness-sink.service` outright. That is
"remove the loudness", explicitly rejected by the user.

## 8. TRAPS HIT TODAY — read before repeating the work

1. **`pkill`/`pgrep -f` self-match.** A pattern matching your own bash command
   kills your own shell → **exit 144**, chain dies silently. Happened 5+ times.
   Use a bracket (`pgrep -f 'fire[f]ox'`) or match by PID.
2. **Headless `dump()` output is unreliable** when other Firefox instances run
   (launches get remoted into the existing instance). **Working method:** page
   writes its result into `document.title`; launch with
   `MOZ_APP_REMOTINGNAME=<unique> --new-instance --name <unique>`; read with
   `xwininfo -root -tree | grep -oE '<TOKEN>[^"]*'`.
3. **Stale probe windows give false readings.** A pre-build probe window still
   showing the old result was misread as a regression. **Kill prior probe windows
   and confirm which PID owns the window before trusting a title.**
4. **`-O3` inlines constexpr / anon-namespace classes** — `strings`/`nm` showed
   **0** `AudioPsychoacousticEnhancer` symbols in libxul even though the code is
   compiled in and running. **Verify by call site, not by symbols.**
5. **Build discipline** (AGENTS.md): `env -u CLAUDECODE ... ./mach build ... |
   tee log; BUILD_EXIT=${PIPESTATUS[0]}` — a piped `$?` is **tee's**. Then verify
   `libxul.so` **mtime moved**; exit 0 + stale mtime = silent failure.
6. **tshark cannot identify WhatsApp call codecs.** Media is TURN-encapsulated
   (port 3478) and SRTP-encrypted; the SDP travels inside WhatsApp's encrypted
   WebSocket. Use `chrome://webrtc-internals` → "Download the PeerConnection
   updates and stats data". (`turnchannel` dissection yielded nothing, and a
   128-byte snaplen truncates payloads anyway.)
7. **Do not enable the webrtc-internals audio/packet/datachannel recorders and
   walk away** — they wrote **931 MB** into `~/Downloads` in minutes (aecdump
   500 MB, wavs 100 MB each), and the DataChannel logs contain message traffic in
   plaintext/base64. Deleted this session.
